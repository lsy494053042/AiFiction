# 写作知识系统

最后更新：2026-04-03

## 1. 这份文档是干什么的

这是一份统一收口文档，只回答这 4 个问题：

1. 写作知识系统现在已经做到哪了
2. 这套系统由哪些层组成，各层负责什么
3. 它是怎么持续迭代而不越堆越乱的
4. 当前先搁置、以后再做的事情有哪些

后面这块不再拆成很多散文档，统一收在这里。

## 2. 当前结论

**写作知识系统 V1 已经闭环。**

这里说的“闭环”是指：

1. 写完一批正文
2. 生成批次复盘
3. 产出：
   - `review.md`
   - `review.json`
   - `knowledge-candidates.json`
4. 候选经验入库
5. 候选经验升级或废弃
6. profile 建立与绑定
7. gate 结果回写
8. 下一次写作包按预算消费规则

也就是说，这条链已经不是“设计草案”，而是能运行的最小系统。

## 3. 项目定位

AiFiction 不是模板堆栈器，也不是规则收集器。

它的定位始终是：

**一个帮助长篇创作低负担、高可控地持续写下去的创作操作系统。**

所以写作知识系统存在的意义不是“多存规则”，而是：

- 避免重复犯错
- 让经验自动沉淀
- 让下一批写作直接受益
- 让总库可以增长，但工作集始终精简

## 4. 五层结构

### 4.1 创作真相层

位置：

- `books/作品名/00-设定`
- `books/作品名/01-大纲`
- `books/作品名/02-正文`

职责：

- 保存真正创作内容
- 作为作品内容真相源

不负责：

- 保存规则状态
- 保存批次 gate
- 保存结构化知识生命周期

### 4.2 控制协议层

位置：

- `workspace.yml`
- `book.yml`

职责：

- 当前写哪本书
- 当前写到哪一卷哪一章
- 当前批次和 gate
- 当前启用哪些知识流程开关

不负责：

- 承载长篇写作经验正文
- 承载规则详细解释

### 4.3 结构化知识层

位置：

- SQLite / V2 数据层

职责：

- 结构化世界状态
- 结构化写作知识状态
- 批次复盘记录
- profile / rule binding
- 应用记录
- gate 记录

这是“方法账”的正式归宿。

### 4.4 Markdown 视图层

位置：

- `templates/writing/*.md`
- `books/作品名/00-设定/文风与写作卡.md`
- `03-中间产物/*.md`

职责：

- 提供人类可读版本
- 提供模板和说明

不应该继续承担：

- 结构化规则唯一真相源

### 4.5 运行时上下文层

位置：

- `03-中间产物/context-packs`

职责：

- 写作包
- 风险排查包
- 当前批次最小工作集

允许重建，不承担长期维护压力。

## 6. 生命周期与治理

### 6.1 知识对象

当前统一只看这几类对象：

- `batch`
- `finding`
- `knowledge_item`
- `profile`
- `profile_rule`
- `application`
- `gate`

### 6.2 生命周期

所有知识对象统一走这些状态：

- `candidate`
- `active`
- `book_only`
- `validated_global`
- `merged`
- `archived`
- `deprecated`

含义：

- `candidate`
  - 新发现，先观察
- `active`
  - 当前生效
- `book_only`
  - 只对当前书有效
- `validated_global`
  - 已验证为跨书有效
- `merged`
  - 被并入更高层规则
- `archived`
  - 保留历史，不进入当前工作集
- `deprecated`
  - 证明无效或有害

### 6.3 反馈分级

不是所有反馈都同权。

- `tier_1`
  - 专业作者反馈
  - 多位真实读者强共识反馈
- `tier_2`
  - 系统批次检查
  - 结构化复盘结果
- `tier_3`
  - AI 检测结果
  - 单次主观感受

优先级：

`tier_1 > tier_2 > tier_3`

### 6.4 升级 / 降级规则

升到 `book_only`：

- 同一本书连续 2 次批次命中
- 或 1 次 `tier_1` + 1 次批次验证

升到 `validated_global`：

- 两本书里都有效
- 或 3 次独立批次有效，且至少 1 次来自稳定 `tier_1 / tier_2`

降到 `archived`：

- 连续 3 个批次没使用
- 当前阶段不再活跃

降到 `deprecated`：

- 明显导致文本僵化
- 与更高优先级规则冲突
- 多次被高权重反馈证明有害

### 6.5 规则优先级

冲突时裁决顺序：

1. 硬约束
2. 本书专属规则
3. 已验证通用规则
4. 候选经验
5. 探索性尝试

### 6.6 活跃工作集预算

允许总库增量，不允许当前工作集无限膨胀。

当前预算建议：

- 活跃通用规则：`8-12`
- 活跃本书规则：`8-12`
- 当前批次重点问题：`3-5`
- 本书活跃规则总量：`15-20`
- 已验证通用规则总量：`20-30`

超限时必须：

- 合并
- 归档
- 废弃

## 7. 已落地的数据库对象

当前知识系统已经不再只是“草案”，这些对象已经进入代码和数据层：

- `knowledge_batches`
- `knowledge_findings`
- `knowledge_items`
- `knowledge_applications`
- `knowledge_gates`
- `knowledge_profiles`
- `knowledge_profile_rules`

当前已实现能力：

- 候选经验入库
- 候选经验升级为 `book_only / validated_global / deprecated`
- profile 自动建立
- profile rule 绑定
- 写作包读取 profile 规则
- 应用结果回写：
  - `helpful / neutral / harmful`
- gate 回写：
  - `passed / blocked / waived`

## 8. 当前可执行闭环

当前可执行闭环是：

1. 写完一批正文
2. 生成批次复盘
3. 产出：
   - `latest-review.md`
   - `latest-review.json`
   - `latest-knowledge-candidates.json`
4. 将候选经验入库
5. 进行升级 / 废弃决策
6. 绑定到 global / book profile
7. 写回 application result 和 gate
8. 下一次写作包按预算读取

这就是 V1 闭环。

## 9. 当前从《末站执灯人》提炼出的候选经验

来源：

- 《末站执灯人》前 10 章专业作者反馈

当前候选经验：

1. 强钩子次章必须先接
2. 悬疑不能遮蔽基础理解
3. 前 3 章必须完成读者入场
4. 每章必须有清楚功能
5. 伏笔要长在因果里，不长在断场里
6. 写后复盘必须检查章节承接，不只检查文风

## 10. 《末站执灯人》当前书级规则重点

当前应写回本书 profile 的重点：

1. 林野“旧站区底层修轨工”身份必须更早钉住
2. 主城 / 旧站区 / 黑市 / 监查处关系必须更早立住
3. 乔宁不能只做信息位
4. 前 10 章优先修承接链，不先加新谜团

## 12. 下一阶段如果要启动，按什么顺序

当前 V1 已闭环，所以不再继续扩新阶段。

后续如果要启动新迭代，建议顺序是：

1. **应用层**
   - 先把知识系统接进页面可视化

2. **增强层**
   - 再补更强的自动分析器和案例库

3. **反馈层**
   - 最后再接入外部反馈与更复杂的验证流

## 13. 一句话总结

**现在这套系统已经能做到：写作 -> 复盘 -> 提炼 -> 升级 -> 再应用。下一阶段不再是补底层，而是把这套闭环更好地接进工作流和页面。**
