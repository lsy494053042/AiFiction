# AiFiction 默认架构收口方案

最后更新：2026-04-08

## 1. 这份文档解决什么问题

这份文档回答的不是“当前某一本书怎么先写下去”，而是：

**AiFiction 如何在不追求完美的前提下，收口成一套能承接大多数小说类型、常见设定复杂度与新书冷启动场景的默认架构。**

目标不是把所有题材一次性做死，而是把系统从“懂的人能绕着用”推进到“普通用户开一本新书，也不会立刻撞到数据层边界”。

## 2. 现状判断

当前项目已经有两层能力：

- 一层是偏固定模型的作品级与写作级结构，擅长承接作品信息、卷章规划、角色资产和常见写作流程。
- 另一层是已经落地的通用实体能力，擅长承接泛化实体、关系、面板、标签、任务和状态。

真正的问题不在于数据库不够强，而在于默认入口还没有完成收口：

- 协议入口仍然偏固定槽位，例如 `source_of_truth` 主要围绕作品定位、世界设定、角色设定、总纲、卷纲。
- 同步入口仍然偏“章节 + 大纲”心智模型，而不是“文档注册 + 结构抽取”心智模型。
- 抽取回写链默认仍然优先写回固定资产，而不是优先沉淀到通用实体层。
- 上下文拼装仍然偏最近章节和最近角色，而不是按任务类型动态取数。

这会导致一个直接后果：

**只要换一本书、换一种题材、换一种组织方式，就会重新怀疑是否要改数据层。**

这不是使用者的问题，而是默认架构姿势还没有彻底切换。

## 3. 目标态

默认架构收口后的目标态应满足以下四条：

1. 新开一本书时，优先配置文档与模板，不优先改 schema。
2. 新出现一种设定时，优先新增实体类型、面板模板或抽取规则，不优先加表。
3. 普通用户即使不了解内部实现，也能按默认流程开书、写设定、做大纲、沉淀结构化资产。
4. 强类型表继续保留使用价值，但不再决定系统对世界的理解边界。

一句话概括：

**AiFiction 的默认底座应当是“通用叙事操作系统”，而不是“某一类小说工作台”。**

## 4. 默认架构原则

### 4.1 文件仍然是真相源

- 人类创作内容仍然首先写在 `books/...` 的 Markdown 文档里。
- 数据库承接的是结构化状态、来源链、投影视图和运行时产物，不替代原文档。
- 页面、上下文包、抽取结果都不能反向篡改真相源的边界。

### 4.2 默认入口必须从固定槽位转向文档注册

后续默认入口不应再依赖有限的固定字段组合，而应支持统一的文档注册模型。

每份文档至少应有这些元信息：

- `doc_kind`
- `template_key`
- `relative_path`
- `scope`
- `is_source_of_truth`
- `priority`
- `sync_policy`

典型 `doc_kind` 包括但不限于：

- `project-brief`
- `world-setting`
- `character-setting`
- `organization-setting`
- `mechanism-setting`
- `outline-master`
- `outline-volume`
- `chapter-draft`
- `review-note`

固定的 `source_of_truth` 字段可以保留，但应降级为兼容入口，而不是长期主结构。

### 4.3 默认落库目标必须是通用实体层

后续新增的结构化信息，默认优先落到以下泛化对象：

- `source_document`
- `entity`
- `entity_alias`
- `entity_edge`
- `panel_template`
- `panel_field`
- `entity_panel_value`
- `entity_tag`
- `task_template`
- `task_requirement`
- `task_assignment`
- `entity_task_match`
- `entity_state_event`
- `source_ref`

只有当某类对象在绝大多数项目中都有稳定且高频的消费场景时，才考虑提供强类型投影或缓存层。

### 4.4 强类型表是投影视图，不是宇宙真理

`character / volume / chapter / world_rule` 这类结构仍然有很强的产品价值，但它们应该被视作：

- 常用投影
- 高性能兼容层
- 写作体验优化层

而不是默认的唯一承接方式。

新的题材、新的组织形态、新的任务体系，原则上都先走通用实体层，再根据需要投影出角色卡、卷纲、章卡、规则卡等视图。

### 4.5 模板注册表是承接题材差异的主机制

题材差异不应该通过不断改主表来解决，而应该通过模板注册来解决。

模板至少应覆盖三类能力：

- 文档模板：定义一类文档如何被识别、如何参与校验、如何参与上下文拼装。
- 实体模板：定义某类实体需要哪些面板字段、标签分类、任务匹配键。
- 工作流模板：定义不同任务类型需要什么上下文、什么 gate、什么抽取与写回规则。

例如：

- `character-core`
- `organization-ecology`
- `faction-network`
- `power-system`
- `resource-economy`
- `task-system`
- `mystery-investigation`

新增题材时，优先新增模板和模板字段，而不是新增数据库主表。

### 4.6 必须有未知类型回退

系统必须允许“暂时不理解”的信息先落地，而不是因为没有专门模型就阻断使用者。

默认回退策略应为：

- 先保留原文来源。
- 尽量落为 `generic entity + source_ref`。
- 如果连实体都无法稳妥抽取，也至少落成带来源定位的候选记录。
- 等到模板补齐后，再把历史候选补写成结构化事实。

这条规则很关键，因为它决定了系统面对新题材时是“可降级”还是“直接卡死”。

### 4.7 上下文拼装必须任务化

后续上下文包不应再默认围绕“最近章节 + 最近角色”来拼。

更合理的方式是按任务类型拼装：

- 设定整理：优先取规则、组织、机制、资源、势力网络。
- 大纲规划：优先取目标、阶段、冲突、已知约束、关键实体关系。
- 正文写作：优先取当前章节相关角色状态、近期事件、伏笔、必要规则。
- 复盘审校：优先取变更记录、来源链、问题实体、冲突事实。

也就是说，**上下文是为任务服务，不是为表结构服务。**

### 4.8 必须默认支持来源链与人工覆盖

结构化系统好不好用，不只看“能不能存”，还看“出错时能不能纠正且不被后续流程覆盖掉”。

默认必须具备：

- 字段级来源定位
- 结构化事实的置信度与验证状态
- 人工覆盖优先级
- 自动回写不得覆盖人工确认结果

## 5. 推荐的默认分层

建议把未来默认架构稳定成五层：

### 5.1 真相源层

- Markdown 文档
- 作品协议

### 5.2 注册与同步层

- 文档注册
- 文件扫描
- 文档识别
- 来源链绑定

### 5.3 通用叙事实体层

- 实体
- 关系
- 面板
- 标签
- 任务
- 状态事件

### 5.4 投影与兼容层

- 角色卡
- 卷纲
- 章卡
- 世界规则卡
- 页面专用摘要视图

### 5.5 运行时消费层

- 上下文包
- review / gate
- 工作台
- 后续 UI

## 6. 这套方案对“普通用户开新书”意味着什么

理想的默认流程应该是：

1. 创建作品目录与协议。
2. 选择一组基础模板。
3. 注册几类核心文档，而不是先手填固定槽位。
4. 扫描文档后，系统优先生成通用实体与来源链。
5. 需要时再生成角色卡、卷纲、章卡等投影。
6. 若出现新设定，优先补模板，不优先改库。

普通用户不需要知道内部是 `entities_v2` 还是 `panel_templates_v2`。
他只需要知道：

- 我写哪类文档
- 系统能抽出什么
- 不够时该补模板还是补文档

这才叫默认架构收口。

## 7. 当前阶段不做什么

这份方案明确不追求以下目标：

- 不要求一次性推倒现有 V2 结构。
- 不要求把所有 Markdown 全量结构化。
- 不要求先做复杂 UI。
- 不要求先做全自动抽取替代人工。
- 不要求为每一种题材预置完整行业包。

当前目标只是把“默认入口、默认落库、默认回退、默认上下文”这四件事收稳。

## 8. 完全插件化的执行顺序

完全插件化不是无限分轮的小补丁，而是固定的 8 个阶段。

依赖顺序如下：

- 阶段 1 和阶段 2 必须先做。
- 阶段 3、阶段 4、阶段 5 可以在阶段 2 完成后并行推进。
- 阶段 6 负责把阶段 3 到阶段 5 的结果统一收口。
- 阶段 7 建立安装与工作区消费能力。
- 阶段 8 做迁移、回归和最终验收。

### 推荐执行批次

为了避免轮次过多、节奏失控，实际执行不建议按 8 轮拆开跑，而建议压成 3 个大步。

#### 大步 1：插件底座批次（阶段 1 + 阶段 2）

范围：

- 阶段 1：插件底座与边界重定义
- 阶段 2：Manifest 与注册表

这一大步做完后，应一次性交付：

- 插件能力模型
- core / plugin 边界
- manifest 结构
- 插件注册表
- 内置插件发现与装载入口

为什么合并：

- 阶段 1 不落到注册表，边界只是文档口径。
- 阶段 2 没有阶段 1 的边界，又很容易变成另一套硬编码。

所以这两步应该视为一个完整批次，一次做完。

#### 大步 2：核心能力插件化批次（阶段 3 + 阶段 4 + 阶段 5）

范围：

- 阶段 3：文档类型与抽取器插件化
- 阶段 4：上下文包与 Gate 插件化
- 阶段 5：Projection 与视图插件化

这一大步做完后，应一次性交付：

- 文档识别与抽取插件化
- context selector 与 gate policy 插件化
- projection / 视图插件化
- 通用实体层到视图层的完整插件消费链

为什么合并：

- 这 3 个阶段本质上都在解决“插件如何真正接管系统主流程”。
- 如果拆成 3 轮，最容易出现“抽取插件化了，但上下文和视图还没跟上”的半成品状态。

所以这 3 步应该视为一个完整批次，一次收口。

#### 大步 3：可用性与收官批次（阶段 6 + 阶段 7 + 阶段 8）

范围：

- 阶段 6：插件隔离、版本与冲突处理
- 阶段 7：插件打包、安装与工作区配置
- 阶段 8：迁移、回归与最终验收

这一大步做完后，应一次性交付：

- 版本、冲突、启停、降级、回退
- 插件安装与工作区配置能力
- 兼容迁移、回归样本和最终验收

为什么合并：

- 这 3 个阶段都属于“让插件化从研发态走向可交付态”。
- 如果拆得太细，会长期停留在“功能看起来有了，但普通人还不能稳用”的中间态。

所以这 3 步也更适合作为一个收官批次完成。

### 执行建议

后续默认按下面的节奏推进：

1. 大步 1：插件底座批次
2. 大步 2：核心能力插件化批次
3. 大步 3：可用性与收官批次

也就是说：

- 文档里保留 8 个阶段，是为了边界清楚。
- 实际实施按 3 个大步推进，是为了减少轮次、方便把控。

### 阶段 1：插件底座与边界重定义

- 冻结 core 与 plugin 的职责边界。
- 定义插件可注册对象类型。
- 明确插件不能碰的底层区域。

入口条件：

- `4 + 1` 核心文档口径已经固定。
- 当前主架构已经明确以通用实体层为主干。

核心交付物：

- 插件能力模型
- core / plugin 边界清单
- 插件生命周期草案
- 内置插件声明骨架

完成标志：

- 代码里已经能表达“什么是插件”。
- 后续新增能力不再默认先塞回 core。

主要风险：

- 边界没定死，后面会继续一边插件化、一边把业务逻辑写回 core。

### 阶段 2：Manifest 与注册表

- 建立插件 manifest。
- 建立插件发现、注册、启停、枚举能力。
- 把模板注册从代码硬编码改成注册表驱动。

入口条件：

- 阶段 1 的能力边界和插件对象模型已经稳定。

核心交付物：

- manifest 结构
- 注册表服务
- 内置插件发现与装载入口
- 模板注册入口

完成标志：

- 系统能列出当前有哪些插件、版本和能力范围。

主要风险：

- 注册表做成另一套硬编码，只是把分散逻辑换了个地方堆。

### 阶段 3：文档类型与抽取器插件化

- 把 `doc_kind / template_key / extractor` 迁到插件侧。
- 提供默认回退插件。
- 让新增文档类型主要通过插件接入。

入口条件：

- 阶段 2 的注册表可以稳定装载插件。

核心交付物：

- 文档识别插件接口
- 抽取器插件接口
- 默认回退插件
- 现有文档抽取的插件化迁移

完成标志：

- 现有设定文档抽取不再依赖 core 硬编码。

主要风险：

- 抽取迁移不彻底，表面插件化，实际关键逻辑仍绑在 core。

### 阶段 4：上下文包与 Gate 插件化

- 把 context selector 做成插件能力。
- 把 gate policy 做成插件能力。
- 让正文、大纲、设定整理、审校复盘拿不同的上下文切片。

入口条件：

- 阶段 2 完成。
- 至少已有一条可运行的抽取插件链。

核心交付物：

- context selector 插件接口
- gate policy 插件接口
- 写作包、风险包、审校包的插件接入点

完成标志：

- 不同任务类型可以拿到不同的上下文切片。

主要风险：

- 继续沿用“最近章节 + 最近角色”的旧拼装习惯，导致插件接口空有其表。

### 阶段 5：Projection 与视图插件化

- 把角色卡、卷纲、章卡、规则卡等降为 projection。
- 让不同题材通过插件生成不同视图。
- 不再让强类型视图反向限定底层结构。

入口条件：

- 阶段 2 完成。
- 通用实体层与来源链已能稳定承接底层事实。

核心交付物：

- projection 插件接口
- 强类型视图的 projection 化迁移方案
- 视图生成与消费约定

完成标志：

- 新视图类型不再需要改核心主表。

主要风险：

- 旧强类型视图和新 projection 双轨长期打架，反而增加复杂度。

### 阶段 6：插件隔离、版本与冲突处理

- 增加插件版本约束。
- 增加冲突检测、启停、降级与回退。
- 保证单个插件出错不会拖死整条主链。

入口条件：

- 阶段 3 到阶段 5 至少有基本可运行实现。

核心交付物：

- 版本约束
- 冲突检测
- 启停与降级策略
- 错误隔离与诊断规则

完成标志：

- 插件出错时，系统能明确报错并回退，而不是把库或流程搞脏。

主要风险：

- 只做“能跑通”的演示级插件化，没做可维护性，后面一样返工。

### 阶段 7：插件打包、安装与工作区配置

- 让插件支持安装、移除、升级、降级。
- 让工作区可以声明启用哪些插件。
- 提供默认插件包和题材插件包。

入口条件：

- 阶段 6 已提供稳定的版本、冲突和回退基础。

核心交付物：

- 插件安装与移除流程
- 工作区插件配置
- 默认插件包
- 题材插件包

完成标志：

- 普通用户不改 core，也能启用一组插件开工。

主要风险：

- 插件只是开发者自用，不具备工作区级真实消费能力。

### 阶段 8：迁移、回归与最终验收

- 兼容旧协议、旧抽取链与旧投影。
- 跑多题材样本回归。
- 固定最终验收清单。

入口条件：

- 前 7 个阶段已具备基本能力闭环。

核心交付物：

- 旧链路兼容迁移
- 多题材回归样本
- 冲突与降级回归
- 最终验收清单

完成标志：

- 至少 2 到 3 本不同类型作品能稳定跑通。

主要风险：

- 新链路看起来很先进，但旧项目和真实样本一跑就碎。

## 9. 完成定义与验收标准

当以下条件同时成立时，才可以认为默认架构已经从“收口”走到“完全插件化”：

1. 新文档类型主要通过插件注册，不需要修改 core 主流程。
2. 新抽取规则主要通过插件注册，不需要修改 core 主流程。
3. 新上下文策略主要通过插件注册，不需要修改 core 主流程。
4. 新 gate 规则主要通过插件注册，不需要修改 core 主流程。
5. 新 projection / 视图主要通过插件注册，不需要修改 core 主流程。
6. 插件具备版本、冲突处理、启停、回退与兼容迁移能力。
7. 新开一本常见题材小说，不需要改数据库 schema。
8. 未知类型信息不会阻断流程，至少能以候选或通用实体方式落地。

每个阶段结项时，还必须补齐这 5 项：

1. 本阶段实际交付物
2. 验证命令与验证结果
3. 当前残留风险
4. 下一阶段入口条件
5. 是否需要更新核心文档

## 10. 这些都做完后，能达到什么目标，能做什么

做完这 8 个阶段后，AiFiction 至少要达到下面 3 层目标。

### 10.1 架构层目标

- 新书冷启动不再先担心数据库结构够不够。
- 新题材接入不再默认改 core schema。
- core 负责稳定底座，插件负责题材、流程与视图差异。
- 旧项目可以留在兼容链上继续运行。

### 10.2 工程层目标

- 新文档类型、新抽取器、新上下文策略、新 gate、新视图都能走插件扩展。
- 常见题材扩展不再一碰就返工主干。
- 安装、启停、冲突、降级与回退有明确机制。
- 普通用户不需要理解内部 schema，也能依赖默认插件包工作。

### 10.3 实际能做的事情

- 开一本新书时，用插件包和文档模板作为入口，而不是先改库。
- 给一本书新增“组织生态”“科研体系”“交易规则”“多小队结构”这类复杂设定时，主要补模板和插件。
- 支持都市异常、群像组织、悬疑调查、经营成长等不同形态共用一套底座。
- 让后续 UI、插件目录、题材包和工作流编排有稳定的底层挂点。

## 11. 插件化完成后的下半场

完全插件化做完，不代表所有事情都结束了。后面还有 6 个模块，但它们属于“产品化和运营化下半场”，不再属于“插件化没做完”。

1. 官方默认插件包
   目标：把最常用的文档、抽取、上下文和 gate 做成官方默认能力。
2. 工作区与开书体验
   目标：让普通用户不理解底层也能开书、选模板、启插件。
3. 迁移与兼容运营
   目标：让旧书、旧协议、旧数据能平稳升级，不反复伤老项目。
4. 质量体系与样本库
   目标：建立多题材样本、golden tests、迁移回归和冲突回归。
5. 插件运维与安全
   目标：补权限、来源信任、依赖冲突、日志、回滚与诊断。
6. 产品层能力与 UI
   目标：继续做插件目录、可视化配置、实体图谱、任务工作流和更好的工作台体验。

### 推荐执行批次

为了避免产品化阶段再次陷入“每轮补一点、长期没有收口”的状态，后续不建议把这 6 个模块拆成很多零碎轮次，而建议压成 3 个大步推进。

#### 大步 1：题材插件包与默认能力批次

范围：
- 官方默认插件包
- 工作区与开书体验中的默认题材能力
- starter profile 向更完整题材插件包的延展

这一大步做完后，至少应该一次性交付：
- 更完整的官方默认插件包
- 更完整的题材插件包骨架
- starter profile / starter bundle / 默认协议覆盖之间的稳定关系
- 推荐形态是 `official-default-*` 负责默认能力，`topic-*` 负责题材组合，旧 `starter-*` bundle 退为兼容 alias
- 对普通用户更顺手的默认开书入口

完成标志：
- 常见题材不再只是 3 套 starter 预设，而是有更完整的官方默认插件包与题材包组合。
- 新开书主要靠选 profile / bundle，而不是再手工拼协议。

#### 大步 2：样本库、Golden 与运维约束批次

范围：
- 质量体系与样本库
- golden tests
- 插件运维与安全中的最小可用约束
- 升级、降级、回滚、冲突与诊断规则

这一大步做完后，至少应该一次性交付：
- 多题材样本库
- starter / protocol / migration 的 golden 基线
- 更完整的回归矩阵
- 插件升级、降级、归一化、回滚和冲突处理约束
- 最小可用的 `normalize / snapshot / doctor / rollback` 运维入口
- `plugin runtime + ops fixture / golden / matrix` 防漂链
- 官方 `topic-*` bundle 的互斥冲突约束与诊断建议

完成标志：
- 不是只有 smoke “能跑”，而是核心题材和关键链路都能“防漂”。
- 后续继续补题材包时，能明确知道哪种改动会破坏既有基线。

收口规则：
- 大步 2 不是“继续发现一个风险就继续往里塞一个子项”，而是只负责把样本库、golden、运维约束做到最小可封口。
- 当 `starter baseline`、`plugin runtime + ops baseline`、`migration / compatibility baseline` 这 3 条基线都齐了之后，大步 2 立即结项。
- 结项后如果再发现新的题材包想法、体验优化或额外样本，不再继续挂进大步 2，而是放入大步 3 或后续 backlog。

结项状态：
- `migration / compatibility baseline` 已补齐。
- 大步 2 到此结项，不再继续扩张；后续新增想法统一进入大步 3 或 backlog。

#### 大步 3：官方默认组合与对外可用性批次

范围：
- 工作区与开书体验的最终收口
- 默认插件包组合
- 更稳定的迁移与兼容入口
- 面向普通用户的最小可交付体验

这一大步做完后，至少应该一次性交付：
- 更完整的工作区初始化与开书初始化组合
- 官方默认插件包与题材插件包的推荐搭配
- 更清楚的迁移/兼容/诊断入口
- 对外可用的最小操作闭环
- 推荐包含一个面向普通使用者的 `quickstart` 入口，把 `workspace:init + books:init + 基本协议验证` 串成单次操作
- 最好进一步把 `doctor / repair` 也统一到 `quickstart` 入口下，避免普通用户自己在多个 CLI 之间手工拼流程

完成标志：
- 不懂内部实现的人，也能比较稳地开书、选题材包、跑初始化和基本验证。
- 我们自己后续开新书，基本不再需要返工底层或补工作流胶水。

关账说明：
- 大步 3 标记为完成，不等于“没有任何后续事项”，而是表示它的阻断性目标已经全部达成。
- 关账后仍然允许保留“已知非阻断遗留项”和“后续优化项”，但这些内容不能继续挂在大步 3 名下无限扩张，而必须转入 backlog。
- 后续如果继续处理这些项，属于新 backlog，不得反过来改写“大步 3 未完成”。

当前已知非阻断遗留项：
- Windows 下部分 smoke 清理临时 SQLite 文件时仍可能出现 `EBUSY`，当前通过延迟清理兜底，但还没有做更彻底的文件句柄收束。
- `quickstart -- repair` 目前会调用既有 CLI，因此输出仍偏工程化，后续可以再收成更简洁的用户态摘要。
- 对外安装、插件目录、信任/签名、图形化配置等“外放产品化”能力仍未进入本轮范围。
- 当前统一入口主要覆盖 `create / doctor / repair`，更深的审校编排、批处理工作流和 UI 引导仍属于后续 backlog。

## 12. 当前结论

AiFiction 接下来不该再围绕“为某一本书补一个字段、补一张表、补一个专用流程”去演进。

更合理的方向是：

**把已经存在的通用实体能力扶正为默认主干，并按 8 个固定阶段完成完全插件化。**

这样系统就不会因为换一本书、换一种类型、换一组设定，就重新回到“是不是又要改数据层”的老问题。

## 2026-04-09 Deferred Trigger Rules

The following items stay in backlog until an explicit trigger fires. They do not reopen closed phases by default.

1. External productization capabilities
   Trigger:
   - a second stable user starts using the system regularly;
   - the tool is being prepared for external delivery instead of internal-only use.
2. Deeper unified workflow entry
   Trigger:
   - at least 1 to 2 books have completed a real writing/review loop;
   - manual command stitching becomes the main source of friction.
3. Full UI guidance, plugin catalog, and install/upgrade flow
   Trigger:
   - ordinary users are expected to onboard without reading the codebase first;
   - plugin distribution or upgrade support becomes a real need.
