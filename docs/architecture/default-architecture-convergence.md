# AiFiction 默认架构收口方案

最后更新：2026-04-13

## 1. 这份文档解决什么问题

这份文档回答的不是“当前某一本书怎么先写下去”，而是：

**AiFiction 如何在保留现有可用底座的前提下，收成一套能承接多数小说类型、常见设定复杂度和新书冷启动场景的默认架构。**

它的任务不是继续堆更多机制，而是把下面这件事说死：

- 什么是项目级稳定地基
- 什么是题材或工作流差异
- 什么是单书特例
- 什么是运行时临时产物

一句话说，这份文档负责把“以后问题该落哪一层”定下来。

## 2. 当前核心判断

当前项目不用推倒重来。

要保留的东西已经很明确：

- 核心文档 `4 + 1`
- `workspace.yml / book.yml` 协议链
- 通用实体层
- 插件底座
- 检查链
- 上下文包链
- CLI / smoke / doctor / quickstart

真正要改的不是“有没有底座”，而是“以后怎么治理”。

当前真正的问题有三个：

1. 一出现单书问题，就容易继续往项目层补规则。
2. 历史兼容口径太多，容易让旧写法反过来决定架构。
3. 正文推进、卷后同步、下一卷放行之间还没有被所有文档统一成一条硬门禁。

所以这一轮收口的重点不是重做底层，而是**冻结治理方式**。

## 3. 目标态

默认架构收口后，至少要满足下面几条：

1. 新开一本书时，优先调题材配置和单书配置，不优先怀疑底层要不要改。
2. 单书问题默认留在单书层或运行时层，不再直接污染项目层。
3. 运行时产物可以帮助推进，但不能反向决定真相源和项目级架构。
4. 一卷正文写完后，卷后同步是真门禁，不是口头提醒。
5. 以后再补智能体、UI、工作流编排，是接在稳定底座上，而不是继续围着历史补丁打转。

一句话概括：

**AiFiction 的默认底座应该是“通用叙事操作系统”，而不是“每换一本书就重新调一轮底层的工作台”。**

## 4. 默认架构原则

### 4.1 文件仍然是真相源

- 人类创作内容仍然首先写在 `books/...` 的 Markdown 文档里。
- 数据库承接的是结构化状态、来源链、投影视图和运行时产物，不替代原文档。
- 页面、上下文包、抽取结果都不能反向篡改真相源边界。

### 4.2 默认入口从固定槽位转向文档注册

后续默认入口不再以固定的 `source_of_truth` 槽位为唯一中心，而要支持统一的文档注册模型。

固定槽位可以保留，但只作为兼容入口，不再作为长期主结构。

后续默认应该由下面这些维度决定文档如何参与系统：

- `doc_kind`
- `template_key`
- `relative_path`
- `scope`
- `is_source_of_truth`
- `priority`
- `sync_policy`

### 4.3 默认落库目标是通用实体层

后续新增的结构化信息，默认优先落到通用对象，而不是优先加强类型表。

优先承接对象包括但不限于：

- `source_document`
- `entity`
- `entity_alias`
- `entity_edge`
- `panel_template`
- `panel_field`
- `entity_panel_value`
- `entity_tag`
- `task_template`
- `task_requirement`
- `task_assignment`
- `entity_task_match`
- `entity_state_event`
- `source_ref`

只有在跨多数作品都稳定高频消费时，才考虑继续做强类型投影或缓存层。

### 4.4 强类型表是投影与兼容层，不是宇宙真理

`character / volume / chapter / world_rule` 这类结构仍然有价值，但它们属于：

- 常用投影
- 高性能兼容层
- 写作体验优化层

不是项目理解世界的唯一方式。

### 4.5 题材差异主要通过模板、规则包和插件承接

题材差异不应该通过不断改主表解决，而应该通过下面这些东西承接：

- 文档模板
- 实体模板
- 工作流模板
- starter profile
- topic bundle
- 官方默认能力组合

也就是说：

- 跨书稳定的题材差异，进题材 / 工作流层
- 单书专属写法和设定，留在单书层

### 4.6 必须有未知类型回退

系统必须允许“暂时不理解”的信息先落地，而不是因为没有专门模型就卡死。

默认回退策略应为：

- 先保留原文来源
- 尽量落为 `generic entity + source_ref`
- 如果连实体都无法稳妥抽取，也至少保留带来源定位的候选记录
- 后续模板补齐后，再把候选补写成结构化事实

### 4.7 上下文拼装必须任务化

上下文包默认不再围绕“最近章节 + 最近角色”来拼，而应围绕任务来拼。

例如：

- 设定整理：优先取规则、组织、机制、资源、势力网络
- 大纲规划：优先取目标、阶段、冲突、约束、关键关系
- 正文写作：优先取当前章节相关状态、近期事件、伏笔、必要规则
- 复盘审校：优先取变更记录、来源链、问题实体、冲突事实

也就是说，**上下文是为任务服务，不是为表结构服务。**

### 4.8 必须支持来源链与人工覆盖

默认必须具备下面这些能力：

- 字段级来源定位
- 结构化事实的置信度与验证状态
- 人工覆盖优先级
- 自动回写不得覆盖人工确认结果

## 5. 两套分层不要混

这里必须分清楚两种“分层”，后面不允许混着说。

### 5.1 技术实现分层

技术上，默认架构仍然按 5 层理解：

1. `真相源层`
   - Markdown 文档
   - 作品协议
2. `注册与同步层`
   - 文档注册
   - 文件扫描
   - 文档识别
   - 来源链绑定
3. `通用叙事实体层`
   - 实体
   - 关系
   - 面板
   - 标签
   - 任务
   - 状态事件
4. `投影与兼容层`
   - 角色卡
   - 卷纲
   - 章卡
   - 世界规则卡
   - 页面摘要视图
5. `运行时消费层`
   - 上下文包
   - gate / review
   - 工作台
   - 后续 UI

### 5.2 问题治理分层

治理上，以后所有新问题默认按 4 层判断归属：

1. `内核层`
   - 跨作品稳定成立的通用能力，例如协议、实体、插件运行时、检查链、上下文主链。
2. `题材 / 工作流层`
   - 平台差异、题材预设、长短篇节奏、试写规则、批处理方式、默认 gate 口径。
3. `单书层`
   - 某一本书自己的设定、权限边界、文风规则、人物规则、剧情约束。
4. `运行时层`
   - 某一卷、某一批、某一次扫描、某一次补丁、某一次复盘、某一次临时回写的产物。

硬规则：

- 单书问题默认不能直接上升为内核问题。
- 运行时问题默认只能在运行时层收口。
- 只有跨书重复出现、并且能稳定复用的问题，才允许提升到题材层或内核层。

## 6. 绿地判断和兼容落地

以后所有新问题，先按没有历史包袱的理想结构判断归属，再决定怎么兼容落地。

这意味着：

- `绿地判断` 是设计标准
- `兼容落地` 是过渡策略

不允许出现下面这种倒置：

- 因为旧写法已经存在，所以默认它就是对的
- 因为某本书已经这么写了，所以项目级架构必须跟着它拐
- 因为当前正文里有某种临时表达，所以核心层必须马上为它让路

兼容可以保留，但兼容不是标准答案。

凡是因为兼容而暂时保留的旧口径，后续都必须能说明它最终准备落回哪一层，不能无限挂着。

## 7. 提升准入规则

一个问题想从单书层或运行时层提升到题材层或内核层，至少要同时满足下面几条：

1. 不是某一本书的局部表达问题，而是跨书都会遇到的稳定问题。
2. 不是一次性补丁，而是后续会被持续消费的通用能力。
3. 放进更高一层后，能减少后续同类问题的重复劳动，而不是只把特殊情况包装得更复杂。
4. 能明确说明它进入高层后，对现有文档、协议、数据、检查链分别产生什么影响。

只要上面四条说不清，就不允许提升层级，继续留在单书层或运行时层解决。

## 8. 当前固定执行计划

这份文档以前承接过“完全插件化”的长路线，但那部分已经属于历史完成项，不再是当前主线。

当前默认执行口径固定为 `3 步`，不再拆成“第一步第一轮、第二轮、第三轮”。

### 8.1 第 1 步：冻结地基

目标：

- 把项目级边界、分层、准入、兼容、卷后门禁一次锁死。

必须收完的东西：

- 技术分层和治理分层的区别
- 绿地判断原则
- 兼容保留原则
- 提升准入规则
- 卷后同步硬门禁
- 当前唯一主线和 backlog 入口

完成标志：

- 核心文档已经能回答“这个问题该落哪一层”
- 后续不再靠聊天临时裁决架构归属

### 8.2 第 2 步：跑通执行闭环

目标：

- 把 `核心文档 / 协议 / 单书真相源 -> 状态快照 -> 检查器 -> 上下文包 -> 正文推进 -> 卷后同步` 这条主链一次串通。

必须收完的东西：

- 写前、写中、卷后分别调用什么
- 扫描、检查、回写、同步的默认入口
- 哪些东西按组轻检，哪些东西必须卷后统一收
- 当前已有底座如何接入这条主链

完成标志：

- 新开一本书时，默认流程能一口气说清楚
- 正在推进的一本书时，知道正文推进和卷后同步分别怎么执行

### 8.3 第 3 步：单书试点并收总尾

目标：

- 只拿一本真实作品把这套闭环跑一遍，并把当前遗留问题统一收口。

当前试点书固定为《灰雾雇员》。

必须收完的东西：

- 用真实卷级推进验证“正文推进 -> 卷后同步 -> 下一卷”是否稳定运转
- 把当前暴露的问题按新分层口径重新归类
- 把不该进项目层的东西留在单书层或运行时层
- 把真正缺的项目级能力汇总成最终补单，而不是边写边补总架构

完成标志：

- 试点作品能稳定按卷运转
- 项目层、单书层、运行时层边界不再混用
- 当前这一轮基础治理正式关账

### 8.4 执行规则

- 当前优化固定为 3 步，不再新增主步骤。
- 每一步必须一次做完、一次关门；未达到完成标准，不进入下一步。
- 当前步骤里发现的新问题：
  - 会阻断当前步骤完成的，当步一次收掉；
  - 不阻断的，统一记入最终收口清单，等 3 步全部完成后一起处理。

## 9. 卷后同步硬门禁

对写作链来说，卷后同步不是可做可不做的整理动作，而是正式门禁。

硬规则如下：

- 一卷正文写完后，必须先完成整卷扫描、问题收口、设定回写、状态同步和必要检查。
- 上述动作没完成前，下一卷最多只能停留在准备态，不能算正式放行。
- 运行时产物、聊天结论、临时记忆，不能代替卷后同步结果。

这条规则的目的不是增加流程，而是防止“正文已经往后写了，设定和状态还停在上一卷”的失控。

## 10. 完成定义与验收标准

这一轮收口完成，不等于“项目没有后续工作”，而是指默认底座已经进入稳定治理态。

至少要同时满足下面几条：

1. 新问题先能归层，再能落地，而不是先吵要不要改核心。
2. 新开一本书时，默认不会立刻撞到数据层边界。
3. 单书问题能留在单书层解决，不再反向污染项目层。
4. 卷后同步真的是门禁，而不是口头要求。
5. 默认运行闭环可以稳定复述，也可以稳定执行。

## 11. 这些都做完后，能达到什么目标，能做什么

做完这 3 步后，AiFiction 至少应该具备下面这些能力：

- 开一本新书时，先调题材和单书配置，而不是先怀疑底层要不要改。
- 同一个项目可以承接多本书，而不是每换一本书就重新优化一轮底座。
- 项目层只保留跨书稳定能力，单书层承接作品个性，运行时层承接临时补丁和现场产物。
- 卷级推进、卷后同步、下一卷放行形成稳定门禁链。
- 以后再补智能体、UI、工作流编排时，是接在稳定底座上，而不是继续围着历史补丁打转。

## 12. 当前不做什么

这轮收口默认不做下面这些事：

- 不重开历史“完全插件化第几阶段”
- 不为了某一本书的具体问题直接改项目级核心结构
- 不把 UI、智能体、外放产品化重新拉回当前主线
- 不把聊天结论继续当成长期真相源
- 不把运行时产物反向当成架构裁决依据

## 13. 延后触发项

下面这些东西继续放在 backlog，只有触发条件成立时才重开：

1. `外放产品化能力`
   - 触发条件：
     - 出现第二个稳定使用者；
     - 或项目开始准备对外交付。
2. `更深的统一工作流入口`
   - 触发条件：
     - 至少有 1 到 2 本书跑完真实写作 / 复盘闭环；
     - 手工拼命令开始成为主要摩擦源。
3. `完整 UI 引导、插件目录、安装升级流`
   - 触发条件：
     - 普通用户需要在不读代码的情况下上手；
     - 或插件分发、升级支持成为真实需求。

## 14. 当前结论

AiFiction 当前真正要做的，不是继续堆更多机制，而是把已经有的底座收成一套稳定的治理方式。

一句话概括：

**先把地基和闭环收稳，再用真实作品验证；验证通过后，后续所有迭代都按固定分层和固定流程走。**
