# 数据库 V2 决策地图

这份文档不再讲“为什么要做 V2”，而是直接回答“哪些字段该放哪、哪些结构必须拆表、哪些内容必须版本化”。

## 1. 四种落库方式

### 1.1 正式列

适合放：

- 高频查询字段
- 会参与排序、筛选、聚合的字段
- 会参与工作流分支判断的字段
- 语义已经稳定的核心业务字段

AiFiction 里的典型例子：

- 项目状态、工作流阶段
- 卷序号、章序号、场景序号
- 角色类型、伏笔状态
- workflow 名称、step 类型
- artifact 类型、scope 类型

### 1.2 子表

适合放：

- 一对多或多对多结构
- 需要单独增删改查的对象
- 后续可能单独做排序、版本、审计的对象

AiFiction 里应优先拆成子表的结构：

- 角色别名
- 角色关系
- 章节场景
- 伏笔关联
- pipeline run steps
- prompt template versions

### 1.3 `meta_json`

适合放：

- 系统内部标记
- 运行时附加信息
- 兼容性数据
- 暂时不作为查询条件的技术元数据

不适合放：

- 角色名、章节顺序、项目状态这类核心业务字段
- 未来要拿来筛选和排序的字段

### 1.4 `extra_json`

适合放：

- 实验字段
- 用户自定义字段
- 暂时还没定型的扩展数据
- 后续可能拆正式列的过渡字段

原则：

- 先进入 `extra_json` 不等于永久放 JSON
- 一旦进入高频查询，就应该升格成正式列或子表

## 2. 当前各核心对象的落库决策

### 2.1 项目层

`novel_projects_v2`

- 放身份字段：`id`、`slug`、`title`
- 放总控字段：`workflow_phase`、`status`
- 放活跃引用：`active_profile_id`、`active_guardrail_profile_id`
- 不放过胖的业务配置，避免主表变成“大杂烩”

`project_profiles_v2`

- 放平台、读者、字数、更新节奏等经营配置
- 保留 `profile_key`，支持同一作品维护多套配置
- 未来如果要切“男频版 / 女频版 / 平台差异版”，不用改主表

`guardrail_profiles_v2`

- 放风格边界、禁忌表达、硬约束
- 保留 `profile_key`，支持同一作品维护多套风格/守护规则

`project_tags_v2`

- 标签单独拆表
- 方便做筛选、统计、批量管理

### 2.2 叙事资产层

`characters_v2`

- 只放角色核心身份与成长弧
- 不把别名和关系继续塞 JSON

`character_aliases_v2`

- 用于支持外号、假名、称谓、阶段性称呼
- 必须保留排序字段，避免称呼展示顺序失控

`character_relationships_v2`

- 显式维护人物关系网络
- 后续可以支持关系热度、敌意、信任值、公开关系与私下关系

`chapters_v2`

- 只放章级控制字段
- 正文、审校报告、改写稿不放在章节表，统一走 artifact/version

`chapter_scenes_v2`

- 这是最典型的“早拆比晚拆成本低”的结构
- 场景后续很容易增长出视角、地点、冲突类型、节奏标签、参与角色等字段

`foreshadows_v2` + `foreshadow_links_v2`

- 主表管伏笔本体
- 关联表管伏笔和章节/角色/规则/产物之间的显式连接

`entity_state_snapshots_v2`

- 用统一快照模型承接“角色状态”
- 后面如果需要做地点状态、组织状态、势力状态，不用新起一套状态体系

### 2.3 运行与版本层

`artifacts_v2`

- 表示一个逻辑产物，例如“第 12 章正文”或“第 12 章连续性报告”
- 管理归属范围、当前激活版本等引用信息

`artifact_versions_v2`

- 表示某个逻辑产物的具体版本内容
- 可支持正文、章卡、摘要、审校报告、改写稿等统一版本化

`pipeline_runs_v2`

- 记录一次工作流的顶层运行
- 适合看大状态、归属、整体耗时

`pipeline_run_steps_v2`

- 记录具体步骤
- 为重试、人工打回、agent handoff、LangGraph 节点运行留口

`prompt_templates_v2` + `prompt_template_versions_v2`

- 主表存逻辑身份
- 版本表存具体 prompt 文本
- 后面回溯“哪版 prompt 导致结果变味”时会很关键

## 3. 哪些字段现在就该拆，哪些先放扩展位

现在就该拆：

- 角色别名
- 角色关系
- 章节场景
- 伏笔关联
- pipeline steps
- prompt versions
- artifact 主体与 artifact 版本

可以先放 `extra_json`：

- 某平台专属运营标签
- 非稳定的评分字段
- 临时实验性的章节节奏标签
- 用户自定义补充备注

可以先放 `meta_json`：

- 系统侧同步标识
- 迁移来源信息
- 调试标记
- 内部兼容标记

## 4. 查询与扩展的最低要求

每张 V2 核心表至少满足：

- 有 `status`
- 有 `version`
- 有 `created_at` / `updated_at`
- 有 `deleted_at`
- 有 `meta_json`
- 有 `extra_json`

每个会自然排序的子表至少满足：

- 有 `sort_order`
- 有父级维度下的唯一顺序约束

每个会长期沉淀内容的对象至少考虑：

- 是否需要独立 artifact
- 是否需要历史版本
- 是否需要和 pipeline run step 建立关联

## 5. 当前阶段的结论

现阶段最重要的不是把所有表一次写满，而是把“分类方式”写对。

只要这几条边界先稳定下来：

- 项目层和叙事资产层分开
- 长文本统一走 artifact/version
- 可增长结构优先拆子表
- 系统元数据和业务扩展统一走双扩展位
- 工作流运行至少保留 run + step 两层

那后面继续长功能，大概率都属于局部增量，而不是数据库推倒重来。
