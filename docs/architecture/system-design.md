# AiFiction 系统设计

最后更新：2026-03-27

## 1. 设计目标

当前系统目标不是构建一个先天自治的 Agent 群，而是先把“长篇小说的结构化控制底座”搭稳：
- 本地正文持续推进
- 自动维护优先
- 人工主要负责审查与判断
- 数据、流程、提示词和运行轨迹都可追踪

## 2. 分层设计

### 2.1 `packages/schemas`
负责领域契约与结构化 schema，是作品、角色、章节、状态等对象的统一接口层。

### 2.2 `packages/data`
负责持久化与查询，是当前项目的核心数据底座。当前已经拆成：
- V2 项目目录层
- V2 叙事资产层
- V2 运行产物层
- V2 自动同步层
- workbench 读写服务层

### 2.3 `packages/core` / `packages/prompts`
负责工作流组装、prompt 模板和后续生成阶段的上下文组织。

### 2.4 `apps/worker`
负责后台任务入口。当前除章节预览链外，还提供目录同步 CLI 入口。

### 2.5 `apps/web`
负责工作台界面。当前页面已经从“重手工录入”向“自动维护 + 待审查 + 手工兜底”收口。

## 3. 真相源设计

系统当前采用 4 层真相分工：
- 本地正文层：本地目录中的正文、大纲、导出物
- 结构化资产层：作品、角色、关系、卷章、伏笔、时间线等核心事实
- 运行产物层：摘要预览、抽取预览、artifact、run log、snapshot
- 审查层：`asset_updates_v2` 和 `review_queue_v2` 中的建议更新与待判断项

核心原则：
- 不依赖把整本正文硬塞进 prompt 里维持长期记忆。
- 长期记忆由系统维护，不由模型“硬记”。
- AI 主要处理新增或修改章节带来的增量变化。
- 高风险改动先进入审查，不直接覆盖事实层。

## 4. V2 数据底座是否足够

结论：足够，当前不需要推倒重来。

当前 V2 已具备 4 类核心能力：
- 项目目录：作品与 profile
- 叙事资产：角色、关系、卷章、伏笔、时间线
- 运行产物：artifact、version、run、snapshot
- 自动同步：file source、source document、review queue、source refs

后续再迭代，主要是继续加读模型、服务层、辅助表和处理规则，不是重建主 schema。

## 5. 当前主链

当前已经落地的链路如下：
1. 绑定作品本地目录
2. 扫描目录下的章节 / 大纲 / 导出文件
3. 生成摘要预览与结构化抽取预览
4. 写入待审查项与来源引用
5. 在工作台中按“变更包”进行审查
6. 把通过的候选回写到结构化事实层

## 6. 当前抽取与回写策略

当前“摘要 + 抽取”还不是最终版模型抽取器，而是一个稳定的首版接口：
- 先把同步、审查、回写主链跑通
- 再逐步把启发式预览替换成更真实的模型抽取

当前已覆盖的候选预览：
- 角色
- 关系
- 伏笔
- 时间线

当前已正式写回事实层：
- 角色候选
- 关系候选
- 伏笔候选
- 时间线候选

## 7. 当前 UI 收口原则

当前工作台的方向不是“让用户填满后台”，而是：
- 首页先找书、看状态、继续处理
- 详情页先看总览和待处理，再按需下钻
- 手工维护只作为兜底入口

详情页当前分为：
- 总览
- 待处理
- 剧情资产
- 高级维护

## 8. 当前最紧急的问题

当前最紧急的问题不是继续补底层能力，而是继续降低人工占比：
- 审查机制还要继续收口
- 冲突处理还要补强
- 低风险自动通过还要再扩大覆盖范围
- 影响分析还要继续升级为更明确的处理动作

因此当前优先级应调整为：
1. 强化来源引用与冲突处理
2. 扩大低风险自动通过
3. 让影响分析更可执行
4. 最后再推进更真实的模型抽取与关系图谱

## 9. 机器上下文层

- 仓库新增了一层“机器上下文”配置，用来承接不同电脑上的路径、SSH、Git 安全目录和本地端口差异。
- 机器上下文的读取顺序是：`config/machine-profiles.json` -> `config/machine-overrides.local.json` -> 运行时探测。
- 这一层不参与业务事实建模，只服务于本地开发执行链，避免把电脑差异硬编码进 skill、文档或临时命令。

## 10. 编码稳定性策略

- 仓库文本文件统一使用 UTF-8 与 LF，编辑器侧通过 `.editorconfig` 和 `.vscode/settings.json` 固定编码。
- 对中文内容的批量更新，优先使用显式 UTF-8 写入方式，不依赖 PowerShell 默认输出编码。
- `scripts/encoding-check.mjs` 负责在提交前发现明显的问号污染、替换字符和常见乱码信号。

### 自动分流（2026-03-28）
- SyncReviewQueueService 已新增项目级自动分流入口，用于批量扫描 pending review，并自动通过低风险项。
- 工作台读模型会同时输出自动接收、需要复核、存在冲突 3 类变更包计数。

## 处理策略分层（2026-03-28）
- WorkbenchActionPlan 现在除了 lane，还会显式给出 strategy。
- 当前策略层包括：自动写回、先核对证据、等待更多上下文、先处理文件格式、先解决事实冲突。
- 读模型会把待处理包优先分成自动接收、复核、冲突三条路径，再决定页面展示和后续动作。

## 影响分析输出（2026-03-28）
- WorkbenchImpactSummary 现在除了 topEntries，还会输出 recommendedReviewChapters。
- 项目级读模型会把这些章节聚合成 attentionChapters，供待处理页和详情页直接消费。
- 这一步还没有进入独立数据库表，当前仍然是读模型聚合结果，优先用于工作台决策和后续复核提示。

## 后续章节动作分流（2026-03-28）
- `attentionChapters` 不再只输出总量，而是增加 `followUpMode`、`priority`、`recommendedAction`。
- 当前分流规则是：冲突包、事实冲突、多次重复命中的后续章节进入 `formal-review`；其余进入 `watch`。
- 这一层仍然是读模型增强，没有新增主表，也没有改动 V2 事实层结构。

## followUpQueue（2026-03-28）
- 工作台读模型在 attentionChapters 之上继续提供项目级 follow-up 聚合，用于突出正式复核章节。
- 这一层仍然是读模型增强，没有新增表，也没有改动 V2 持久化结构。

## formalReviewTasks（2026-03-28）
- followUpQueue 之上继续提供 formalReviewTasks，用于承接章节级正式复核任务。
- 这仍然属于读模型增强，数据库结构未变。

## 正式复核任务状态持久化（2026-03-28）
- 新增 `follow_up_task_states_v2`，按 `(projectId, chapterId, taskKind)` 唯一约束存储后续任务状态。
- 这张表不复制整个 follow-up 任务载荷，只保存任务指纹、任务状态和处理备注，仍然由 workbench 读模型实时派生任务内容。
- 读模型合并逻辑会对比 task fingerprint：指纹未变且状态为 `completed` / `dismissed` 时，任务不再出现在活跃队列中；指纹变更后自动重新开启。

## 关系图谱视图（2026-03-28）
- Web 详情页现在有独立 `graph` 视图，读模型仍然直接复用 `WorkbenchProjectSnapshot.graph` 和 `recentSourceRefs`。
- 这一版暂不新增新的图谱存储表，仍然以现有结构化关系事实和来源引用作为真相源。

- 关系图谱视图已接入 URL 驱动的角色聚焦和来源类型筛选，便于后续继续扩展可点击来源引用。
- 图谱视图与待处理视图已通过 sourceDocumentId/sourcePath 打通来源追踪链，支持按来源回看同源变更包。
- follow_up_task_states_v2 已补充任务结果字段，用于记录 formal-review 的处理结果与结果摘要。

## 最新设计决策（2026-03-28 / 自动维护链闭环）
- 自动分流只作用于本次 sync run 内新生成的审查项，避免把历史 pending review 一起卷入。
- 低风险 review item 会自动调用既有 decideReviewItem -> writeback 链，不再停留在纯预览层。
- 同步 run item 会根据 source document 的最新 syncStatus 回写为 auto_applied / review_pending / review_rejected，便于后续观察。
