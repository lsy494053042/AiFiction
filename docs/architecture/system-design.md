# AiFiction 系统设计

最后更新：2026-03-31

## 1. 设计目标

AiFiction 当前的设计目标不是先做一个复杂的 Agent 系统，而是先把这件事做稳：

**让一部长篇小说能够在“本地文件 + 协议锚点 + 数据库 + 工作台”这条链上稳定跑起来。**

当前阶段的设计重点已经调整为：

- 先真实试写 `末站执灯人`
- 再根据真实使用反馈继续优化

## 2. 四层结构

### 2.1 创作文件层

这一层是真正的创作内容：

- 设定文件
- 大纲文件
- 正文文件

它们默认放在：

```text
books/作品名/
```

这是人和 Codex 真正持续协作的主战场。

### 2.2 协议锚点层

这一层的核心是：

- `workspace.yml`
- 每本书自己的 `book.yml`

它们不是数据库替代品，而是：

- 入口
- 锚点
- 状态定位文件

它们回答的问题是：

- 当前有哪些书
- 这本书在哪里
- 当前写到哪
- 接下来应该优先读什么

### 2.3 数据层

数据层是结构化真相层，当前以 SQLite 为主。

它负责保存：

- 角色
- 角色别名
- 关系
- 伏笔
- 时间线
- 同步记录
- 待处理项
- 来源引用
- 正式复核任务状态

### 2.4 工作台层

工作台层由 Web 与 Worker 组成。

它负责：

- 同步本地目录
- 阅读作品内容
- 展示作品当前状态
- 暴露少量需要处理的例外问题

## 3. 现在最重要的设计原则

### 3.1 作品优先，不是系统优先

用户默认应该看到的是：

- 这本书写到哪了
- 正文是什么
- 大纲是什么
- 设定是什么
- 只有最后才是需要处理的问题

不该默认看到：

- 协议文件
- 路径
- 上下文包
- 内部术语

### 3.2 默认自动维护，人工只处理例外

系统负责：

- 同步
- 抽取
- 低风险自动处理
- 事实回写
- 来源追踪

用户负责：

- 定方向
- 看结果
- 拍板高风险变化
- 做少量纠错

### 3.3 协议文件不是第二个数据库

`workspace.yml` 和 `book.yml` 只存关键锚点信息。

不要把这些内容塞进去：

- 全部角色详情
- 全部关系网
- 全部伏笔
- 全部时间线
- 全部历史任务

这些都应该在数据库里。

## 4. 现在的正式页面结构

当前正式 Web 只保留两条主路由：

- `/`
- `/works/[slug]/[view]`

单本书当前拆成 6 个内容页：

- `总览`
- `正文`
- `大纲`
- `角色`
- `设定`
- `待处理`

这比之前把所有东西堆在一个长页面里更符合用户心智。

## 5. 真相层与锚点层的关系

### 创作文件层

负责保存：

- 作品定位
- 世界设定
- 角色设定
- 大纲
- 正文

### 协议锚点层

负责告诉系统：

- 当前作品目录在哪里
- 当前阶段是什么
- 当前焦点任务是什么
- 最近应该优先读什么

### 数据层

负责保存：

- 结构化事实
- 审查结果
- 同步状态
- 来源引用

### 上下文包层

负责给智能体准备：

- 写作包
- 风险排查包

也就是说：

**文件负责创作内容，协议负责入口和定位，数据库负责结构化真相，上下文包负责让智能体快速开工。**

## 6. 8 个优化点与当前状态

### 1. Proposal / Commit

- 当前状态：半完成
- 已有提案与审查层
- 但还没有完全收口成统一提案模型

### 2. CQRS-lite

- 当前状态：基本完成
- 读模型和写模型已经分开

### 3. 事件日志 + 快照

- 当前状态：半完成
- 有快照，有运行记录
- 但没有完整统一的全局事件模型

### 4. 稳定 ID + 别名层

- 当前状态：角色层已完成
- `characters_v2 + character_aliases_v2` 已落地
- 但地点、势力、物品、规则项还没有完全推广

### 5. 阶段驱动

- 当前状态：半完成
- 底层已有阶段与焦点
- 前台还没有完全做到按阶段自动收口

### 6. 上下文包生成器

- 当前状态：第一版完成
- 写作包与风险排查包已可生成

### 7. 策略引擎

- 当前状态：第一版完成
- 已有风险判断与动作分发规则

### 8. 前台任务队列 / 后台维护队列分离

- 当前状态：半完成
- 底层分层已存在
- 前台还需要继续隐藏无用内部概念

## 7. 当前阶段怎么和这些优化点兼容

当前阶段不会先把这 8 个点全部补满。

当前策略是：

- 先正式写 `末站执灯人`
- 让真实使用暴露最痛的点
- 再决定下一轮优先补哪一条

这样做的原因很简单：

- 现在再继续抽象，很容易原地打转
- 先用真实作品，能最快暴露哪些优化点最值钱

## 8. 当前阶段之后的下一阶段

当 `末站执灯人` 跑起第一轮真实创作后，下一阶段的重点会切到：

1. 压缩页面里无用信息
2. 提高低风险自动通过覆盖率
3. 继续隐藏系统内部概念
4. 优先补真实试写里最痛的优化点

## 9. 当前设计结论

当前项目的关键不再是“还缺多少底层”，而是：

**现有底层已经够支撑一次真实试写，接下来应该先真实使用，再基于真实反馈做下一轮优化。**


## 写作知识库数据库草案

当前阶段已经确认：写作知识库不是全部放数据库，也不是全部留在 Markdown。

更合理的分层是：

- 数据库存骨架：结构化规则、标签、状态、版本、适用范围
- Markdown 存细节：完整说明、风格解释、示例段落、长文本分析
- 上下文包负责把两边组装起来，给 Codex 或其他智能体直接使用

### 继续留在 Markdown 的内容

下面这些不适合直接塞数据库：

- 完整文风说明
- 示例段落与反例段落
- 长篇角色分析
- 讨论过程与草稿过程

原因很简单：这类内容更依赖上下文、语气和长文本表达，数据库不适合承载它们的主表达。

### 与现有数据层的兼容方式

当前 V2 数据层已经有一些可复用基础：

- guardrail_profiles_v2
  可继续承载禁忌表达、风格锚点、硬约束
- characters_v2.speechGuide
  可继续承载角色说话导向
- world_rules_v2
  可复用来表达作品级长期规则
- entity_state_snapshots_v2
  可继续承载角色、势力、组织等阶段状态
- prompt_templates_v2 / prompt_template_versions_v2
  可支持写作模板和版本控制

也就是说，下一阶段不需要推翻重做，而是：

- 在现有表上复用一部分能力
- 再补少量“写作知识库专用表”

### 下一阶段建议新增的表

如果后面正式落库，优先级建议如下：

1. chapter_function_types_v2

4. ook_writing_profiles_v2

### 当前阶段的策略

当前阶段先不急着把这些表全部做出来。

更合理的顺序是：

1. 继续真实试写《末站执灯人》
2. 先用 Markdown 卡片沉淀规则
3. 把反复稳定、反复验证有效的部分，再提升到数据库层

一句话：

**先让知识长出来，再把稳定的部分结构化。**
