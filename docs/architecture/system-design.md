# AiFiction 系统设计

最后更新：2026-03-26

## 1. 设计目标

当前系统目标不是构建一个先天自治的 Agent 群，而是先把“长篇小说的结构化控制底座”搭稳：
- 本地正文持续推进
- 自动维护优先
- 人工主要负责审查与判断
- 数据、流程、提示词和运行轨迹都可追踪

## 2. 分层设计

### 2.1 `packages/schemas`
负责领域契约与结构化 schema，是作品、角色、章节、状态等对象的统一接口层。

### 2.2 `packages/data`
负责持久化与查询，是当前项目的核心数据底座。当前已经拆成：
- V2 项目目录层
- V2 叙事资产层
- V2 运行产物层
- V2 自动同步层
- workbench 读写服务层

### 2.3 `packages/core` / `packages/prompts`
负责工作流组装、prompt 模板和后续生成阶段的上下文组织。

### 2.4 `apps/worker`
负责后台任务入口。除章节预览链外，当前还提供目录同步 CLI 入口：`src/sync-runner.ts`。

### 2.5 `apps/web`
负责工作台界面。当前页面已经从“重手工录入”向“自动维护 + 待审查 + 手工兜底”的结构收口。

## 3. 真相源设计

系统当前采用 4 层真相分工：
- 本地正文层：本地目录中的正文、大纲、导出物。
- 结构化资产层：作品、角色、关系、卷章、伏笔、时间线等核心事实。
- 运行产物层：摘要预览、抽取预览、artifact、run log、snapshot。
- 审查层：`asset_updates_v2` 和 `review_queue_v2` 中的建议更新与待判断项。

核心原则：
- 不依赖把整本正文硬塞进 prompt 里维持长期记忆。
- 长期记忆由系统维护，不由模型“硬记”。
- AI 主要处理新增或修改章节带来的增量变化。
- 高风险改动先进入审查，不直接覆盖事实层。

## 4. V2 数据底座是否足够支撑当前改造

结论：足够，不需要推倒重来。

当前 V2 已具备 4 类核心能力：
- 项目目录：作品与 profile
- 叙事资产：角色、关系、卷章、伏笔、时间线
- 运行产物：artifact、pipeline run、snapshot、prompt registry
- 自动同步：file source、source document、sync run、asset update、review queue、source ref

因此这轮改造的方式是“增量扩表 + 服务层接入 + UI 收缩”，而不是重建数据库。

## 5. 自动同步主链

当前已经落地的链路如下：
1. 为作品绑定本地目录源。
2. 扫描目录下的章节 / 大纲 / 导出文件。
3. 将文件索引写入 `source_documents_v2`。
4. 将运行轨迹写入 `sync_runs_v2` / `sync_run_items_v2`。
5. 为新增或修改文件生成摘要预览 artifact。
6. 为新增或修改文件生成结构化抽取预览 artifact。
7. 生成 `asset_updates_v2` 建议更新。
8. 生成 `review_queue_v2` 待审查项。
9. 通过 `source_refs_v2` 记录源文档与产物引用关系。
10. 在 Web 中消费待审查项，并把审查结果写回审查层与源文档状态。
11. 对通过的角色 / 关系 / 伏笔 / 时间线候选执行首版事实回写。

## 6. 当前抽取与写回策略

当前“摘要 + 抽取”还不是最终版模型抽取器，而是一个稳定的首版接口：
- `.md` / `.txt` 走本地启发式分析。
- `.docx` 先进入待审查队列。
- 摘要结果统一进入 artifact/version 体系。
- 抽取结果统一进入 artifact/version + `asset_updates_v2`。
- 待审查项统一进入 `review_queue_v2`。

当前已覆盖的候选预览：
- 角色候选
- 关系候选
- 伏笔候选
- 时间线候选

当前已正式写回事实层：
- 角色候选
- 关系候选
- 伏笔候选
- 时间线候选

为了让伏笔和时间线的事实回写稳定，系统会在必要时：
- 自动为源文档创建占位卷
- 自动为源文档创建占位章节
- 将 `source_documents_v2` 映射到该章节范围

这样可以保证“来自本地目录但尚未手工建章”的正文，也能有稳定的事实归属点。

## 7. 当前 UI 收口原则

首页默认只保留：
- 作品总览
- 快速创建
- 帮助入口

作品详情页默认只保留：
- 本地目录与自动维护
- 待审查队列
- 结构化资产概览
- 关系预览
- 折叠后的手工维护兜底入口

设计目标是把工作台定位成“查看和判断”，而不是“把所有字段都摊开手填”。

## 8. 已知问题

- 抽取层仍是启发式预览，离更真实的模型抽取还有一段距离。
- 当前的事实回写虽然已经覆盖角色、关系、伏笔、时间线，但冲突合并与高置信度判定还需补强。
- `.docx` 尚未接入正式解析器。
- SQLite 在高并发写入时可能出现锁冲突，因此当前验证链以串行为主。
- Web build 如果和 dev 进程同时抢 `.next/trace`，可能出现文件锁；停掉 dev 后重跑即可。

## 9. 下一阶段设计重点

1. 为事实写回补来源引用与冲突处理。
2. 继续压缩首页与详情页中的手工维护负担。
3. 为关系图谱、来源引用和影响分析留出更明确的页面入口。
4. 逐步把更真实的模型抽取与审查策略接进当前链路。
